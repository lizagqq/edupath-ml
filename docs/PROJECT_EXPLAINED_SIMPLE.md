# Как я разрабатывала EduPath ML: понятное объяснение для подготовки к защите

Официальная тема: **«Разработка программного комплекса для оценки уровня знаний и формирования индивидуальных траекторий обучения»**.

Материал подготовлен по текущему коду, журналу разработки и сохранённым отчётам. Актуальный интерфейс — версия 0.2.0: «Профиль ученика», «Анализ знаний», «План обучения».

Это учебное объяснение, а не текст, который нужно выучить дословно. В каждом шаге сначала дана формулировка от первого лица, затем объяснение её смысла. Если термин незнаком, его можно посмотреть в словаре в конце.

## Как понимать последовательность разработки

Нумерация ниже показывает **логичный порядок объяснения проекта**. В действительности некоторые части создавались и проверялись одновременно, а затем дорабатывались. Приписывать каждому файлу точную дату создания по имеющимся сведениям нельзя.

В журнале подтверждена следующая история. Сначала из-за недоступности загрузки данных и пакетов основа программы проверялась на искусственных примерах. Затем 9 ноября 2026 года в проект был добавлен настоящий CSV ASSISTments, выполнены его анализ, очистка и обучение. После этого развивались материалы, рекомендации и интерфейс. Позднее библиотека выросла до 23 записей, а выбор тем стал персональным. После пользовательской проверки в браузере исправлена защита обмена данными между сервером и интерфейсом, а интерфейс переработан в учебное приложение с тремя разделами.

**Все итоговые числа качества модели в этом материале относятся к реальному ASSISTments.** Ранние искусственные примеры нужны были для проверки программы и не доказывали качество на настоящих учениках. После последних изменений рекомендаций и интерфейса модель не переобучалась.

## Шаг 1. Определение задачи

### 1. Что я сделала

«Сначала я определила, какую проблему должна решать программа. Итоговая оценка показывает общий результат ученика, но не всегда объясняет, какие темы ему нужно повторить. Я решила разработать приложение, которое использует историю математических ответов, показывает результаты по отдельным навыкам и помогает выбрать последовательность повторения».

### 2. Зачем я это сделала

Представь двух учеников с одинаковой отметкой за контрольную. Один ошибается с дробями, другой — с геометрией. Общая отметка одинаковая, а дальнейшая работа нужна разная. Программа помогает преподавателю увидеть эту разницу без ручного просмотра всей истории ответов.

Для этого недостаточно просто вывести список ошибок: нужно связать возможное затруднение с подходящим объяснением и понятным порядком работы.

### 3. Как это работает

В приложение поступают уже существующие ответы из образовательной системы. Пользователь выбирает ученика и видит, по каким математическим навыкам есть наблюдения, как он отвечал раньше и что модель прогнозирует для следующего задания по теме. Затем приложение предлагает короткий план повторения с материалами.

Здесь важно различать три действия. Подсчитать прошлые правильные ответы — это описание истории. Оценить вероятность следующего правильного ответа — прогноз. Выбрать темы и их порядок — рекомендация. В проекте они связаны, но не заменяют друг друга.

### 4. Что получилось

Было определено назначение EduPath ML: **дополнительный аналитический инструмент для преподавателя и обучающегося**. Он не заменяет образовательную платформу, не ведёт учебные курсы и не проводит новое оцениваемое тестирование. Формулировка темы про оценку знаний реализована через анализ результатов и прогноз, а не через точное измерение того, насколько ученик знает весь предмет.

### 5. Что может спросить преподаватель

**В чём практическая проблема?** Итоговый балл недостаточно подробно показывает, что именно повторять. Мой инструмент связывает историю ответов с конкретными темами и материалами.

**Кто пользуется программой?** Преподаватель может анализировать профиль и обсуждать план с учеником; обучающийся может использовать подготовленные шаги для повторения.

**Почему это не полноценная система дистанционного обучения?** Здесь нет управления курсами и нового оцениваемого тестирования. Основная работа начинается с готовой истории из другой системы.

## Шаг 2. Поиск и выбор датасета

### 1. Что я сделала

«Мне были нужны реальные примеры учебной деятельности. Для проекта я выбрала ASSISTments Skill Builder 2009–2010 — набор данных о выполнении математических заданий. В проект была добавлена локальная исправленная выгрузка, а её происхождение я проверила по официальной странице и метаданным загрузки».

### 2. Зачем я это сделала

Датасет — это собранный набор примеров. Чтобы учить программу прогнозировать ответы, нужны ситуации, в которых уже известно, кто решал задание, к какому навыку оно относилось и каким был результат.

ASSISTments подходит по составу: в нём есть ученики, математические навыки, ответы и порядок событий. Не пришлось придумывать результаты учеников или вручную собирать большую учебную историю.

### 3. Как это работает

Источник — [официальная страница ASSISTments Skill Builder 2009–2010](https://sites.google.com/site/assistmentsdata/home/2009-2010-assistment-data/skill-builder-data-2009-2010). Она отдельно указывает исправленную версию после обнаружения дублированных записей. Использованный файл называется `skill_builder_data_corrected_collapsed.csv`.

Слово **collapsed** означает, что несколько меток навыков одного ответа могут быть записаны вместе, например через подчёркивания. В проекте такая запись сохраняется целиком как отдельный идентификатор.

Точная история поиска во всех браузерных вкладках не записана. Подтверждено другое: сначала загрузку в среде разработки блокировала сеть, затем пользователь добавил локальный файл. В его Windows-метаданных был тот же идентификатор Google Drive, на который ссылается официальный источник. Поэтому корректно говорить о проверенном соответствии источнику по метаданным, а не о том, что программа сама успешно скачала файл. Независимой контрольной суммы от издателя нет.

### 4. Что получилось

В `data/raw/` появился реальный CSV размером **64 412 812 байт**, примерно 64,4 МБ. Исходный файл сохранён отдельно и при обработке не переписывался. Его локальная контрольная сумма записана в отчёте: она позволяет заметить последующее изменение файла, но сама по себе не заменяет подтверждение от издателя.

### 5. Что может спросить преподаватель

**Почему вы выбрали именно ASSISTments?** В нём есть необходимая связь между учеником, математическим навыком и правильностью ответа, а также порядок событий.

**Вы сами собрали эти ответы?** Нет. Использована открытая исследовательская выгрузка существующей образовательной системы.

**Данные настоящие или искусственные?** Итоговый эксперимент выполнен на настоящих данных. Искусственный набор использовался только на раннем этапе, когда реальная загрузка была недоступна.

## Шаг 3. Изучение датасета

### 1. Что я сделала

«Перед обучением я изучила устройство файла: посчитала строки, учеников и навыки, проверила столбцы, пропуски и повторения. Это помогло понять, какие записи пригодны для моей задачи и как правильно читать историю ученика».

### 2. Зачем я это сделала

Большая таблица не обязательно является готовым материалом для обучения. Если непонятно, что обозначает строка или отсутствует тема задания, модель может учиться на неправильно истолкованных примерах. Сначала нужно разобраться с данными, а уже затем применять алгоритм.

### 3. Как это работает

В исходном CSV **346 860 строк и 31 столбец**. Важные поля можно объяснить так:

| Поле | Простой смысл | Роль в проекте |
|---|---|---|
| `user_id` | Номер ученика | Собрать его историю и отделить группы учеников |
| `skill_id` | Код проверяемого навыка | Связать ответы, прогнозы и материалы |
| `skill_name` | Название навыка | Показать тему человеку |
| `problem_id` | Номер задания | Изучить структуру и повторы; не входит в модель как признак |
| `order_id` | Порядковый номер события | Определить, какие ответы были раньше |
| `correct` | Правильно ли ответил ученик: 1 или 0 | Результат, который модель учится предсказывать |
| `attempt_count` | Число попыток | Изучается как поле исходника, но не используется для прогноза текущего ответа |
| `hint_count` | Число подсказок | Также не используется для прогноза текущего ответа |

Были обнаружены пропуски идентификаторов и названий навыков. Некоторые разные ID имели одинаковое название. Также встретились **4779 повторных пар «ученик — задание»**, но с разным порядком события. Они могли обозначать повторные попытки, поэтому автоматически удалять их как дубликаты было бы неправильно.

По `order_id` совпадений не обнаружено. Это помогает восстановить порядок, но не даёт точного календарного времени между ответами. В неиспользуемом поле текста ответа встретились пять некорректных байтов кодировки.

### 4. Что получилось

Было установлено, что нужно различать **код навыка**, его **название** и отдельное **событие ответа**. После очистки в анализ вошли 149 ID и 112 различных значений названий. Это не основание объединить одноимённые навыки: у них могут быть разные истории.

Сведения об исходнике сохранены в `reports/raw_eda.json`, о подготовленных данных — в `reports/eda.json`. Такой предварительный обзор часто называют исследовательским анализом данных: сначала понять таблицу, а затем строить модель.

### 5. Что может спросить преподаватель

**Одна строка — один ученик?** Нет, одна строка — запись об ответе. У одного ученика много строк.

**Почему 149 навыков, но только 112 названий?** У разных идентификаторов могут совпадать названия. Кроме того, при пропуске названия его заменяли самим кодом.

**Почему повторное задание не удалили?** У повторов разный порядок событий. Это могли быть отдельные попытки, которые нужны для истории.

## Шаг 4. Подготовка данных

### 1. Что я сделала

«Я проверила обязательные значения, исключила непригодные строки и упорядочила ответы каждого ученика. Затем для каждого события рассчитала показатели, которые описывают только предшествующую историю».

### 2. Зачем я это сделала

Модель не может осмысленно оценивать результат по теме, которую невозможно определить. Ей также нужны признаки — короткое числовое описание того, что известно об ученике перед новым заданием. Сырые строки сами по себе такого описания не дают.

### 3. Как это работает

Загрузчик проверяет ученика, навык, порядок события и правильность ответа. Результат должен быть равен 0 или 1, порядок — быть корректным числом. Значения вроде пустой строки или `NA` распознаются как пропуски.

В этой выгрузке исключены **63 755 строк без пригодной идентификации навыка**. Если код навыка был, а название отсутствовало, строку сохраняли: код по-прежнему позволяет учитывать ответ. Таких строк с ID, но без названия было **8515**. Содержание неизвестной темы при этом не придумывалось. Загрузчик в общем случае умеет использовать доступное название при отсутствии кода, но в фактической очищенной выгрузке аудит подтвердил именно указанные исключения.

Для каждого ответа создавались четыре основных исторических показателя:

1. Сколько заданий ученик отвечал до этого события.
2. Как часто он отвечал правильно в общей прошлой истории.
3. Сколько ответов уже было по этому навыку.
4. Как часто он отвечал правильно именно по этому навыку.

Также учитывался сам идентификатор навыка. Счётчики преобразуются так, чтобы очень большие числа не подавляли остальные признаки. Доли успеха слегка сглаживаются: к числу успехов добавляется 1, а к числу ответов — 2. Например, 7 успехов из 10 превращаются для модели в 8/12, примерно 0,667. Это не изменение реальной статистики: пользователю отдельно доступна обычная историческая доля 7/10.

**Почему нельзя использовать будущие ответы?** Представь, что нужно предсказать результат третьего задания. Уже известны первые два ответа, но третий и четвёртый ещё не произошли. Если включить их в среднюю успешность, получится подсматривание в ответ. На бумаге модель станет выглядеть лучше, но в реальной работе такой информации у неё не будет.

Поэтому программа сначала записывает признаки очередного события, и только потом добавляет его результат в историю. Текущие подсказки и число попыток также не используются: они могут стать известны уже во время решения и раскрыть результат.

### 4. Что получилось

Осталось **283 105 ответов 4163 учеников**. Правильных — **186 322**, ошибочных — **96 783**, то есть примерно **65,81%** ответов правильные. Использованы все пригодные строки, а не небольшая выборка из них. Чистый CSV сохранён в `data/demo/interactions.csv`, исходный — отдельно в `data/raw/`.

### 5. Что может спросить преподаватель

**Почему нельзя просто заменить все пропуски нулями?** Пропущенный код темы не означает тему с номером ноль, а отсутствие истории не означает, что ученик всё решил неправильно.

**Что такое утечка данных?** Это попадание в прогноз сведений, которых в момент реального решения ещё не должно быть, например текущего правильного ответа.

**Модель использует подсказки?** Нет. Текущие подсказки и попытки в признаки не входят. Используются предыдущие результаты и навык.

## Шаг 5. Выбор и обучение модели машинного обучения

### 1. Что я сделала

«Я реализовала логистическую регрессию, которая по истории ученика и навыку оценивает вероятность следующего правильного ответа. Для подбора её параметров использовала стохастический градиентный спуск — SGD. Результат сравнила с двумя более простыми способами прогноза».

### 2. Зачем я это сделала

Можно вручную задать правило «мало правильных ответов — низкий прогноз». Но общая успешность, опыт по теме и особенности навыка могут сочетаться сложнее. Обучаемая модель подбирает, насколько важен каждый из этих сигналов, по большому числу уже известных примеров.

Логистическая регрессия подходит как понятный начальный вариант: она возвращает вероятность, относительно проста и позволяет хранить небольшое число параметров. Проект не доказывает, что она лучше всех существующих методов. Случайный лес и нейросети в итоговом сравнении не обучались.

### 3. Как это работает

Модель можно представить как набор настраиваемых коэффициентов. Один коэффициент связан с общей прошлой успешностью, другой — с опытом по теме, отдельные коэффициенты относятся к навыкам. При обучении программа делает прогноз, сравнивает его с настоящим ответом и немного меняет коэффициенты, чтобы уменьшить ошибку.

**SGD** означает, что такие небольшие изменения выполняются последовательно по обучающим примерам. Это способ обучения логистической модели, а не ещё одна отдельная модель.

Простой условный пример: до нового задания ученик ответил 100 раз, из них 70 правильно. По дробям у него 10 ответов, из которых 7 правильных. Модель получает не имя ученика и не готовую оценку «дроби освоены», а числовое описание этой истории и код навыка. Код ученика нужен для сбора истории, но не передаётся модели как отдельный признак. Конкретная вероятность вычисляется по сохранённым коэффициентам; её нельзя получить только из отношения 7/10.

Настоящий пример проекта: у ученика 79021 по площади круга 22 ответа, из которых 6 правильных. Историческая доля — 27,27%, а прогноз модели следующего ответа — 48,30%. Они не обязаны совпадать: модель учитывает и общую историю, и особенности навыка.

При обучении использовались 18 проходов по обучающим примерам. Такой проход называется эпохой. После подготовки исторических признаков примеры внутри обучения перемешивались. Это не нарушает порядок прошлого: сами признаки уже были вычислены до перемешивания и больше не изменялись от него.

### 4. Что получилось

Получена собственная компактная реализация логистической модели на Python, без обучения через scikit-learn. Один сохранённый эксперимент указывает **13,928 секунды** обучения; это время конкретного запуска, а не обещание скорости на любом компьютере.

Параметры сохранены в `models/model.json`. JSON — текстовая запись структурированных данных. При открытии приложения модель читается из файла и применяет готовые коэффициенты. Она не начинает учиться заново при каждом выборе ученика.

### 5. Что может спросить преподаватель

**Чему обучалась модель?** Предсказывать правильность следующего ответа на заданном навыке по предыдущей истории.

**Почему метод называется регрессией, если результат правильный или неправильный?** Логистическая регрессия используется для такой классификации: сначала выдаёт вероятность, затем при необходимости её переводят в класс по порогу.

**Ученик прошёл материал — модель сразу стала лучше?** Нет. Просмотр материала и локальная отметка не создают новый оцениваемый ответ и не меняют коэффициенты.

## Шаг 6. Проверка модели

### 1. Что я сделала

«Я разделила учеников на две непересекающиеся группы. На одной обучила модель, на другой проверила прогноз. Затем сравнила её с постоянной вероятностью и простым правилом по прошлым ответам».

### 2. Зачем я это сделала

Проверять только на обучающих примерах — как оценивать подготовку по тем же билетам, ответы на которые уже разбирались. Нужно увидеть, помогает ли найденная закономерность на других данных. В моём случае важно было отделить именно учеников, чтобы история одного человека не оказалась сразу в двух группах.

### 3. Как это работает

После воспроизводимого перемешивания с фиксированным числом **42** для проверки выделили примерно 20% учеников. Фиксированное число позволяет снова получить тот же состав групп.

| Часть | Ученики | Ответы | Назначение |
|---|---:|---:|---|
| Обучающая | 3330 | 223463 | Подобрать коэффициенты |
| Тестовая | 833 | 59642 | Проверить готовую модель |

Совпадающих ID учеников между группами — **ноль**. При этом в проверке разрешено использовать прошлые ответы тестового ученика для его последующих заданий. Например, перед десятым ответом уже можно знать первые девять. Это применение истории, а не переобучение коэффициентов на тестовых ответах.

Для сравнения использованы три способа:

- **Константа:** вычислить долю правильных ответов в обучающей части и выдавать одну вероятность всем. При пороге 0,5 в данном эксперименте этот метод всегда выбирает класс «правильно».
- **Историческое правило:** оценивать успех по предыдущим ответам на навык, осторожно смешивая его с общей частотой.
- **Logistic SGD:** обученная логистическая модель совместно учитывает несколько признаков.

Метрики означают следующее.

**Accuracy** — сколько ответов удалось отнести к правильному классу. Порог 0,5 переводит вероятность в предположение: от 0,5 — «правильно», ниже — «ошибка». Если из 100 случаев верно определены 71, Accuracy примерно 71%.

**ROC-AUC** — насколько хорошо модель ставит более высокие вероятности тем случаям, где ответ действительно правильный. Здесь 0,5 означает отсутствие различения классов по оценке, а 1 — идеальное ранжирование. Это не ещё одно название процента правильных предсказаний.

**F1** объединяет точность положительных предположений и полноту найденных положительных случаев. В нашем эксперименте положительный класс — **правильный ответ**, не «слабая тема». Простая аналогия: важно не только назвать много ответов правильными, но и не слишком часто ошибаться в этих предположениях. У нашей модели среди ответов, названных ею правильными, действительно правильными были примерно 73,93%. А из всех действительно правильных ответов она распознала примерно 86,70%. Это две стороны оценки, которые объединяет F1. Одной F1 недостаточно: когда правильных ответов много, она может быть высокой даже у очень примитивного метода.

**Log Loss** проверяет качество вероятностей. Уверенная ошибка наказывается сильнее осторожной. Если модель обещает почти 100% успеха, а ученик ошибается, штраф большой. Чем меньше эта метрика, тем лучше. Значение 0,5653 нельзя читать как «56,53% ошибок»: это другая шкала.

Дополнительно рассчитана **оценка Брайера**: средний квадрат разницы между прогнозом и фактическим 0 или 1. Здесь также лучше меньше.

### 4. Что получилось

Это сохранённые результаты на одной и той же тестовой части:

| Метод | Accuracy | F1 | ROC-AUC | Log Loss | Брайер |
|---|---:|---:|---:|---:|---:|
| Константа | 0,6562 | 0,7924 | 0,5000 | 0,6435 | 0,2256 |
| Историческое правило | 0,6862 | 0,7902 | 0,6670 | 0,6069 | 0,2088 |
| Logistic SGD | **0,7121** | **0,7981** | **0,7276** | **0,5653** | **0,1914** |

По Accuracy получилось **71,21% против 65,62%** у константы: преимущество примерно **5,59 процентного пункта**, а не 5,59% относительного роста. Для масштаба это около 56 дополнительных верных классификаций на 1000 проверочных ответов в среднем по этому сравнению.

Log Loss уменьшился примерно на **12,17% относительно константы**. Модель также лучше исторического правила по Accuracy, ROC-AUC и вероятностным ошибкам. F1 выросла немного: это нормально, потому что константа уже получает высокую F1, объявляя все ответы правильными. Её ROC-AUC при этом равна 0,5.

Корректный вывод: **модель лучше выбранных простых методов на данном разбиении**, но ещё ошибается. 71,21% не означает, что она определяет уровень знаний с точностью 71,21%. Не проводились повторения по многим разбиениям и отдельная проверка соответствия всех вероятностей реальным частотам. Не доказано и то, что рекомендации улучшают обучение.

### 5. Что может спросить преподаватель

**Почему нельзя было случайно разделить отдельные ответы?** Тогда один ученик мог бы присутствовать в обеих частях. Разделение по ученикам проверяет работу с другими людьми.

**Почему F1 почти 0,8 даже у константы?** Правильных ответов много, а константа относит все случаи к этому классу. Поэтому дополнительно нужны другие показатели.

**Ваш результат хороший?** Для выбранной задачи модель даёт измеримое улучшение над двумя простыми способами. Но одного эксперимента недостаточно, чтобы назвать её лучшей вообще или доказать педагогическую пользу.

## Шаг 7. Создание базы данных

### 1. Что я сделала

«Для работы приложения я сохранила очищенную историю и справочные сведения в SQLite. Отдельно организовала учеников, навыки, ответы, материалы и предварительные связи между темами».

### 2. Зачем я это сделала

CSV удобен для передачи исходной выгрузки, но приложение должно многократно выбирать небольшие части данных: историю конкретного ученика, материал одной темы, связи перед определённым навыком. База данных позволяет делать это запросами и связывать разные сведения по общим кодам.

### 3. Как это работает

SQLite — система управления базой данных, которой для этого проекта не нужен отдельный сервер. Подготовленное хранилище находится в одном файле `data/demo/edupath.db`.

| Таблица | Что хранит | Сколько записей |
|---|---|---:|
| `students` | Идентификаторы учеников | 4163 |
| `skills` | Идентификаторы и исходные названия навыков | 149 |
| `interactions` | Ответы с учеником, навыком, порядком и результатом | 283105 |
| `materials` | Учебные объяснения, примеры и источники | 23 |
| `prerequisites` | Пары «предварительная тема → зависимая тема» | 5 |

Один ученик связан со многими ответами. Каждый ответ относится к одному сохранённому ID навыка. По тому же ID можно найти материал. Таблица связей говорит, какая тема может требоваться перед другой.

Связующий идентификатор похож на номер читательского билета: по нему можно соединить сведения, не переписывая имя во всех записях. Первичный ключ отличает одну запись от другой. Внешний ключ описывает ссылку на запись другой таблицы.

Техническая подробность на случай уточнения: в существующей схеме внешние ключи объявлены для ответов, но не для материалов и графа. Эти связи поддерживаются программой и аудитом. Нельзя говорить, что SQLite автоматически контролирует все связи проекта. Для истории создан индекс по ученику и порядку: это вспомогательная структура, которая помогает выбирать нужные записи без полного перебора таблицы.

Параметры модели хранятся **отдельно в JSON**, а не в таблице ответов. Это позволяет различать учебные события и обученные коэффициенты.

### 4. Что получилось

Приложение читает подготовленную базу вместо повторной обработки исходного CSV на каждом запросе. SQLite выбрана как простое локальное решение, соответствующее учебному проекту. Отдельный сервер PostgreSQL имел бы смысл при других требованиях, например при множестве одновременно записывающих пользователей; такой режим в проекте не исследован.

### 5. Что может спросить преподаватель

**Зачем база, если уже есть CSV?** CSV — исходная выгрузка. База удобна для повторных выборок и связей: ответы ученика, названия тем, материалы и зависимости находятся согласованными запросами.

**SQLite хранит модель?** Нет, модель хранится отдельно в `models/model.json`. SQLite содержит данные и базу материалов.

**Почему не PostgreSQL?** Для локального приложения достаточно SQLite, которая не требует отдельной настройки сервера. Нагрузочное преимущество одной СУБД над другой я не измеряла.

## Шаг 8. Разработка индивидуальной траектории

### 1. Что я сделала

«Я разработала правила, которые переводят прогнозы в конкретный план повторения. Программа выбирает до четырёх слабых тем с готовыми материалами, добавляет нужные предварительные знания и определяет порядок шагов. Темы без материала не исчезают из анализа: они показываются отдельно».

### 2. Зачем я это сделала

Вероятность сама по себе не подсказывает, что делать дальше. Если у ученика по одной теме прогноз 20%, а по другой 45%, нужно решить, какую тему повторять первой, есть ли к ней материал и не требуется ли перед ней восстановить основу.

Нельзя просто показать весь каталог и назвать его индивидуальным планом. Нельзя также считать самую низкую вероятность единственным правилом порядка: зависимая тема может требовать подготовки.

### 3. Как это работает

**Сначала определяется сигнал затруднения.** По навыку должно быть хотя бы три ответа, а вероятность следующего правильного ответа — ниже 50%. При 3–9 ответах вывод обозначается как предварительный. Один-два ответа не участвуют в таком отборе. Три ответа — установленный порог программы, а не доказательство достаточной статистической надёжности.

**Затем выбирается основное содержание.** Среди слабых навыков с материалами первыми рассматриваются самые низкие прогнозы. Выбираются не более четырёх тем. При одинаковом исходном названии одно вводное чтение не повторяется в основном коротком плане. Но разные ID, их история и вероятности не объединяются.

**После этого проверяется подготовка.** Вручную задан граф предварительных знаний. Например, стрелка «площадь круга → поверхность цилиндра» означает, что первую тему стоит проверить перед второй. Если у предварительной темы прогноз ниже 70% или меньше трёх ответов и для неё есть материал, она добавляется. Если наблюдений достаточно, а прогноз от 70%, отдельный шаг подготовки пропускается.

**Наконец определяется порядок.** У каждого выбранного шага есть числовой приоритет. Его основа — `100 × (1 − вероятность)`: чем ниже прогноз успеха, тем выше приоритет повторения. Это служебный балл, не отметка и не процент освоения. К нему добавляются 15 баллов при менее трёх ответах и 8 баллов при наличии слабой включённой предварительной темы. Для этой последней надбавки слабость основы проверяется по прогнозу ниже 65% либо менее трёх ответов.

Эти пороги выполняют разные роли: 50% — отбор затруднений; 70% — необходимость отдельной подготовки; 65% — вспомогательная надбавка при ранжировании. Они заданы вручную, а не найдены моделью как педагогически оптимальные.

Из тем, которые уже можно проходить, выбирается максимальный приоритет. Если перед темой есть ещё не размещённая подготовка, тема ждёт. Такой порядок называется топологическим: направление стрелок соблюдается. Программа также проверяет, нет ли замкнутого круга зависимостей, где A требует B, а B требует A.

#### Настоящий пример: ученик 79021

В его истории **1061 ответ**, наблюдения есть по **93 навыкам**, минимум три ответа — по **56**. Алгоритм выявляет **17 слабых ID**; у **семи** нет материала.

Четыре основные темы выбираются так: повороты, поверхность цилиндра, отражение и один ID круговых диаграмм. Затем добавляется площадь круга как подготовка. Итоговый порядок отличается от порядка первоначального выбора:

| Шаг | Тема | Ответов по теме | Прогноз правильного следующего ответа | Приоритет | Почему включена |
|---|---|---:|---:|---:|---|
| 1 | Повороты фигур | 3 | 6,87% | 93,1 | Основное затруднение |
| 2 | Отражение фигур | 5 | 21,56% | 78,4 | Основное затруднение |
| 3 | Круговые диаграммы | 4 | 27,61% | 72,4 | Основное затруднение |
| 4 | Площадь круга | 22 | 48,30% | 51,7 | Основа для цилиндра |
| 5 | Площадь поверхности цилиндра | 4 | 18,87% | 89,1 | Основное затруднение; ждёт подготовку |

**Почему цилиндр не второй, хотя прогноз очень низкий?** Его приоритет действительно выше приоритета отражения. Но сначала должна пройти площадь круга. Пока эта подготовка не размещена, цилиндр недоступен. Среди остальных доступных тем первыми оказываются отражение и круговые диаграммы, затем площадь круга. После неё можно поставить цилиндр.

**Почему площадь круга вообще появилась, если её не было среди четырёх основных?** Четыре — ограничение основных тем, а не всех шагов. Формула полной поверхности закрытого цилиндра включает два круглых основания. Поэтому площадь круга нужна по зависимости. Её прогноз 48,30% ниже порога 70%, и отдельный шаг не пропускается. Она и сама удовлетворяет диагностическому порогу 50%, но в данном плане получила роль подготовки, поскольку четыре основных места уже заняты другими темами.

У поворотов всего три ответа, поэтому даже 6,87% нужно обсуждать как предварительный сигнал. Программа не утверждает, что ученик точно не знает повороты.

### 4. Что получилось

Фактический маршрут: **Повороты фигур → Отражение фигур → Круговые диаграммы → Площадь круга → Площадь поверхности цилиндра**.

В базе всего пять вручную заданных зависимостей: умножение перед делением дробей; перевод дробей и процентов перед нахождением процентов и процентом от числа; простые уравнения перед более сложными; площадь круга перед поверхностью цилиндра. Это маленький граф, а не полная карта математики.

Семь слабых ID без материалов у 79021 показаны отдельно. Среди них есть ID 76 без известного названия: содержание этой темы не выдумывается. Некоторые другие слабые темы с материалами откладываются; до трёх выводятся как дополнительное закрепление, полный перечень сигналов остаётся в диагностике. Другой ID круговой диаграммы сохраняется отдельно, несмотря на одинаковое чтение.

Для проверки персонализации сохранены и другие примеры: у 75169 план из двух шагов, у 78970 — из четырёх. Если подходящих тем нет, программа возвращает пустой план с объяснением, а не подставляет всем один каталог.

### 5. Что может спросить преподаватель

**Траекторию строит сама ML-модель?** Модель выдаёт вероятности. Маршрут строит отдельный алгоритм по этим вероятностям, материалам и графу.

**Почему пять шагов, если ограничение четыре?** До четырёх выбираются основные слабые темы. Подготовительные темы добавляются сверх этого количества.

**Почему не включить все обнаруженные затруднения?** Основной план сделан коротким; кроме того, не для всех тем есть материал. Остальные сигналы сохраняются и доступны отдельно.

## Шаг 9. Подбор учебных материалов

### 1. Что я сделала

«Я подготовила небольшую библиотеку объяснений и связала каждый материал с точным кодом навыка. Для выбранного шага добавила цель, теорию, разобранный пример и фиксированные задания с решениями. Также реализовала поиск материалов по словам».

### 2. Зачем я это сделала

Рекомендация «повторить круг» слишком общая. Ученику нужно понимать, что именно изучить, увидеть решение и попробовать применить правило. Связь с конкретным навыком помогает не подменить нужный материал похожим названием.

### 3. Как это работает

Основные записи материалов хранятся в таблице `materials` SQLite: название, объяснение, пример, источник и ссылка. Подготовленные определения есть и в `src/retrieval/materials.py`. Расширенное содержание уроков находится в `src/retrieval/lessons.py` и добавляется программой при чтении. Последняя доработка уроков поэтому не потребовала менять таблицы и данные учеников.

В плане материал находится по точному `skill_id`. Если шаг относится к площади круга, программа берёт карточку именно этого ID. Свободный поиск для этой привязки не нужен.

Для отдельных текстовых запросов в API есть другой механизм. Например, запрос «как умножить дроби» разбивается на слова; программа сравнивает их с названием и объяснением. Учитываются совпадения в заголовке и редкость слова в библиотеке, русские окончания упрощаются по правилам. Это лексический поиск: сопоставление слов, а не полноценное понимание текста. Отдельного поля свободного поиска в текущих трёх пользовательских разделах нет; функция доступна через API.

Большая языковая модель здесь не требуется: библиотека небольшая, объяснения заранее написаны, а связь темы с материалом известна. Программа не сочиняет новый ответ по найденным документам, поэтому называть её полноценной RAG-системой нельзя.

Например, в шаге по цилиндру объясняется, что полная поверхность состоит из двух кругов и бокового прямоугольника. Для радиуса 2 и высоты 3 получается `8π + 12π = 20π` квадратных единиц. В самостоятельном задании радиус 1 и высота 2 дают `2π + 4π = 6π`. Это фиксированные проверенные примеры, а не случайно сгенерированные условия.

### 4. Что получилось

Библиотека содержит **23 записи по ID**, а связанные с ними уроки — **31 запись фиксированных практических заданий**. Часть содержания повторяется для четырёх ID Circle Graph: это не 23 разных курса и не 31 обязательно различная задача. Использованы тематические страницы OpenStax; короткие русские пояснения и задачи подготовлены как собственные учебные заметки.

Учебная самопроверка означает, что пользователь решает задание сам, затем раскрывает ответ и объяснение. Программа не принимает его решение на автоматическую оценку, не сохраняет новую попытку и не меняет прогноз. Локальная отметка шага означает только «я отметил, что разобрал материал».

Материалы связаны с **125 669 ответами**, то есть **44,39%** очищенной истории. Это охват по данным, а не доказательство, что почти половина всех математических знаний обеспечена хорошим учебным курсом.

### 5. Что может спросить преподаватель

**Кто пишет объяснения — нейросеть во время работы приложения?** Нет. В приложении используются заранее подготовленные тексты и фиксированные задачи.

**Чем поиск отличается от выбора материала в плане?** Поиск сравнивает слова запроса с текстами. В плане используется точное соответствие по коду навыка.

**Как вы проверили поиск?** В сохранённом отчёте девять ручных запросов дали нужный материал первым. Это маленькая проверка прежнего ядра библиотеки, а не полная оценка всех 23 записей. При отсутствии совпадений свободный поиск может вернуть слабоподходящий результат.

## Шаг 10. Разработка серверной части

### 1. Что я сделала

«Я связала базу, модель и рекомендации в общий сервис и предоставила доступ к результатам через FastAPI. Благодаря этому интерфейс запрашивает нужные данные, а вычислительная часть готовит согласованный ответ».

### 2. Зачем я это сделала

Пользователь не должен самостоятельно открывать SQLite, считать признаки и запускать функции. Нужна часть программы, которая сделает это по запросу и вернёт готовый результат. Эту вычислительную сторону приложения называют **backend**, или серверной частью.

### 3. Как это работает

**API** — договорённость о том, как одна часть программы обращается к другой. Например, запрос `/students/79021/trajectory` означает «дай профиль и учебный план ученика 79021». FastAPI помогает принимать такие обращения, проверять параметры и возвращать данные в понятном программе формате JSON.

Когда выбран ученик, происходит следующее:

1. Интерфейс отправляет запрос плана для его ID.
2. Общий класс `Service` читает историю из SQLite.
3. Для каждого навыка считает число ответов и прошлую успешность.
4. Загружает готовые коэффициенты модели и вычисляет вероятность следующего ответа.
5. Формирует диагноз-сигналы и выбирает маршрут по правилам.
6. Прикрепляет материалы и отправляет профиль и план одним ответом.
7. Интерфейс проверяет состав ответа и отображает результат.

В текущей версии профиль и план получаются из одного ответа, чтобы не смешивать разные снимки данных. Данные ученика в интерфейсе не кэшируются; краткий кэш остался у списка выбора учеников. Кэш — временно сохранённый ответ, который можно повторно использовать вместо нового запроса.

У API семь прикладных маршрутов. В частности, `/health` сообщает состояние и версии, `/materials` возвращает материалы, `/model/info` — сведения эксперимента. FastAPI также предоставляет страницу документации `/docs`. Она нужна разработчику и проверяющему, а не для прохождения учебных шагов.

### 4. Что получилось

Появилась единая вычислительная часть для основного FastAPI и резервного простого HTTP-сервера. Основная демонстрация учебного приложения использует FastAPI и Streamlit.

После ошибок обмена добавлен **контракт траектории версии 2**. Это проверка, какие поля обязательно должны быть в ответе. Сервер проверяет его перед выдачей, интерфейс — перед показом. Если приходит старый или неполный ответ, пользователь получает понятное сообщение о несовместимости и перезапуске вместо падения страницы.

### 5. Что может спросить преподаватель

**FastAPI обучает модель?** Нет. Это средство организации серверных запросов. Коэффициенты обучаются отдельно, а сервер применяет сохранённую модель.

**Почему сервер и интерфейс разделены?** Так вычисления не зависят от оформления страницы, их можно проверять отдельно, а интерфейс получает готовые данные.

**Что такое контракт API?** Согласованный состав и смысл ответа. Например, интерфейс должен получить список выявленных затруднений и число материалов, а не угадывать их при отсутствии.

## Шаг 11. Разработка интерфейса

### 1. Что я сделала

«Я разработала интерфейс на Streamlit и после обратной связи переработала его из технической панели в три понятных раздела: профиль ученика, анализ знаний и план обучения. Основной акцент сделала на том, что пользователю нужно повторить и как начать».

### 2. Зачем я это сделала

Человек приходит в образовательное приложение не ради внутренних коэффициентов и метрик эксперимента. Ему нужно понять, кто выбран, какие есть результаты, что рекомендуется сделать и почему. Поэтому техническая точность должна сопровождаться ясным представлением.

Видимую пользователю часть обычно называют **frontend**. Streamlit позволяет задавать её средствами Python: выборы, таблицы, кнопки и раскрывающиеся пояснения. Это не отдельный вручную написанный интерфейс на JavaScript; Streamlit сам организует отображение в браузере.

### 3. Как это работает

**Профиль ученика** показывает число ответов на задания, долю правильных, количество тем с наблюдениями и количество тем хотя бы с тремя ответами. Карточки расположены по две в строке, а для узкого экрана предусмотрена одна колонка. Ниже — три наиболее заметных диагностических сигнала и переход к плану. Наличие наблюдений не обозначается как освоение темы.

**Анализ знаний** сопоставляет прошлую успешность и прогноз. Есть число ответов и обозначение предварительных сигналов, отдельные блоки малой и нулевой истории. Подробные ID и исходные названия вынесены в раскрывающуюся часть. Совпадающие названия различаются как «запись 1», «запись 2»: это подписи разных записей, а не выдуманные разновидности математической темы.

**План обучения** объясняет число основных и предварительных тем и показывает их последовательность. Пользователь выбирает шаг, читает цель и теорию, разбирает пример, решает задания и раскрывает решение. Есть кнопки следующего и предыдущего шага. Вся последовательность видна, но полный урок открыт только для выбранного шага — это сокращает длинную прокрутку.

Можно отметить «Я разобрал(а) этот шаг». Отметки разделены по ученикам и навыкам и находятся только в текущей сессии Streamlit. Они не записываются в БД и могут сброситься при новой сессии. Отметка не блокирует переход и не доказывает освоение.

### 4. Что получилось

Актуальная навигация содержит именно три перечисленных раздела. Страница **«Качество модели» удалена из основного пользовательского интерфейса**. Сами метрики сохранены в файлах, документации и API. В боковой панели есть компактная информация о системе.

Поведение элементов проверено автоматически. Адаптивные стили реализованы, но их окончательный внешний вид после последней переработки ещё требует осмотра в настоящем браузере. Наличие правила «одна колонка на узком экране» в коде и подтверждённая визуальная проверка — разные факты.

**Почему Streamlit?** Он позволяет средствами Python быстро собрать понятный интерфейс для аналитических данных, без отдельной сложной клиентской разработки.

**Отметка шага означает, что тема освоена?** Нет. Это личная отметка пользователя в текущей сессии, она не оценивает ответ и не меняет прогноз.

## Шаг 12. Проверка программы и исправление ошибок

### 1. Что я сделала

«Я проверяла не только модель, но и работу компонентов: обработку истории, рекомендации, ответы API и элементы интерфейса. Когда при пользовательской проверке возникли ошибки отсутствующих полей, я добавила проверяемый контракт и проверила совместную работу FastAPI и интерфейса».

### 3. Как это работает

Небольшой автоматический тест задаёт конкретную ситуацию и проверяет ожидаемый результат. Например, предварительная тема должна оказаться раньше зависимой; разные Circle Graph не должны слиться; неизвестный ученик должен получить ответ «не найден», а не чужой профиль.

Пользователь также обнаружил `KeyError: detected_difficulties` и `KeyError: material_count`. Смысл `KeyError` прост: интерфейс попросил поле, которого не оказалось в полученном объекте. В актуальном коде сервиса оба поля уже были, но интерфейс раньше не проверял структуру ответа и временно его кэшировал. Устаревший серверный процесс — вероятное объяснение, но конкретный процесс в пользовательской Ubuntu отсюда подтвердить не удалось. Нельзя выдавать эту гипотезу за установленный факт.

Исправление состояло в согласовании проверки формата на обеих сторонах, добавлении версии и отказе от кэширования данных ученика. Отсутствующие поля не подменяются пустыми списками. В проверке специально воспроизведён старый ответ без обоих полей: теперь UI корректно сообщает о несовместимости.

Совместная проверка подаёт ответы настоящего FastAPI в Streamlit AppTest. AppTest — инструмент, который программно открывает элементы приложения, меняет выбор ученика, нажимает кнопки и проверяет состояние без обычного окна браузера.

MLflow для регистрации экспериментов также не нужно представлять как подтверждённую часть: есть скрипт регистрации готовых результатов, но его работа с установленным MLflow не проверена.

### 5. Что может спросить преподаватель

**Что является главным результатом работы?** Сквозной программный комплекс: реальные ответы превращаются в профиль, прогноз и объяснённый порядок повторения с материалами.

**Доказано, что после маршрута ученики учатся лучше?** Нет. Проверены качество прогноза и техническая корректность правил. Для учебного эффекта нужен отдельный педагогический эксперимент.

**Что требуется перед демонстрацией?** Перезапустить оба процесса, проверить версию API, выполнить сетевые проверки и осмотреть интерфейс. Повторное обучение для этого не требуется.

## Цельный рассказ для преподавателя на 5–7 минут

Рассказ рассчитан на спокойное произнесение с небольшими паузами. Перед встречей стоит один раз прочитать его вслух с таймером: индивидуальная скорость речи различается. Таблицу метрик и подробности формул можно оставить для ответов на вопросы.

### Текст выступления

Моя курсовая работа называется «Разработка программного комплекса для оценки уровня знаний и формирования индивидуальных траекторий обучения». Программный комплекс получил название EduPath ML.

Я исходила из простой проблемы. Итоговая оценка показывает общий результат, но не всегда объясняет, что именно нужно повторить. Например, у двух учеников может быть одинаковая отметка, хотя один ошибается с дробями, а другой — с геометрией. Мне хотелось связать историю ответов с конкретными дальнейшими действиями: показать возможные затруднения и предложить материалы в понятном порядке.

Для этого я выбрала данные ASSISTments о выполнении математических заданий. В них записано, какой ученик отвечал, с каким навыком связано задание и был ли ответ правильным. Сначала доступ к загрузке из среды разработки был ограничен, поэтому основу проверяли на искусственных примерах. Затем в проект был добавлен настоящий файл, соответствующий исправленной выгрузке на официальной странице. Все итоговые результаты получены уже на нём.

Перед обучением я разобралась со структурой таблицы. В исходном файле было 346 860 записей. У части из них отсутствовала пригодная информация о навыке, поэтому такие строки пришлось исключить. Осталось 283 105 ответов 4163 учеников и 149 идентификаторов навыков. Если код навыка был, а название отсутствовало, ответ сохранялся, но содержание темы не придумывалось. Повторные попытки одного задания тоже не удалялись автоматически.

Дальше нужно было представить историю в форме, понятной модели. Для каждого ответа я рассчитывала, сколько ученик уже отвечал раньше, как часто отвечал правильно вообще и что происходило по конкретному навыку. Текущий результат добавлялся в историю только после расчёта признаков. Это важно: если при прогнозировании использовать ещё не произошедшие ответы, программа будет как будто подглядывать в решение. Проверка покажет завышенное качество, которое нельзя повторить в реальной работе.

Для прогноза я использовала логистическую регрессию. Она по числовым показателям истории оценивает вероятность правильного следующего ответа. Её параметры подбираются постепенно: программа сравнивает свой прогноз с известным результатом и исправляет коэффициенты. Такой способ обучения называется стохастическим градиентным спуском. Модель относительно простая и подходит для исходного исследовательского решения. Она не определяет точный процент освоения предмета.

Чтобы проверить результат, я разделила именно учеников: 3330 вошли в обучающую часть, а 833 — в тестовую. Общих учеников между частями нет. На тестовой части проверялась уже готовая модель. Для сравнения взяла самый простой способ, который выдаёт одну вероятность всем, и правило по прошлым ответам ученика.

Модель правильно классифицировала примерно 71,21% тестовых ответов, а постоянный метод — 65,62%. То есть преимущество составило около 5,59 процентного пункта. Показатели качества вероятностей тоже улучшились. Я рассматриваю это как подтверждение того, что история полезна для прогноза на выбранных данных, но не как доказательство безошибочной оценки знаний или эффективности будущего обучения.

Для приложения я создала SQLite-базу. CSV остался исходной выгрузкой, а база позволила отдельно хранить учеников, навыки, ответы, материалы и зависимости между темами. Это удобно, когда нужно много раз получать историю одного человека и связанные с ней сведения. Саму обученную модель я сохранила отдельно, поэтому при открытии приложения повторное обучение не происходит.

Следующая часть — индивидуальный план. Модель даёт вероятность, а отдельный алгоритм решает, что рекомендовать. Сначала он отбирает темы с прогнозом ниже 50% и хотя бы тремя ответами. Из тем с материалами выбирает до четырёх основных, затем добавляет необходимые предварительные знания. Сигналы по небольшой истории прямо обозначаются как предварительные.

Для ученика 79021 получилась последовательность: повороты фигур, отражение, круговые диаграммы, площадь круга и площадь поверхности цилиндра. Здесь четыре основные темы и одна подготовительная. Площадь круга добавлена потому, что нужна для площади оснований цилиндра. Поэтому цилиндр идёт позже, хотя его прогноз хуже. Порядок определяется не только срочностью, но и зависимостями. Темы, для которых материала пока нет, остаются в отдельном списке.

В библиотеке 23 записи по навыкам. Для шагов подготовлены цели, небольшая теория, разобранные примеры и задания с раскрытием решения. Объяснения не генерируются во время работы. Материал маршрута связан с точным кодом навыка, а для текстовых запросов отдельно реализован поиск по словам. Поэтому большая языковая модель здесь не понадобилась.

Серверную часть я организовала через FastAPI, интерфейс — через Streamlit. При выборе ученика сервер читает историю, применяет готовую модель, строит план и возвращает данные для страницы. В актуальном интерфейсе три раздела: профиль ученика, анализ знаний и план обучения. Учебный шаг можно отметить как разобранный, но это только отметка текущей сессии: она не оценивает знания и не меняет прогноз.

В ходе проверки обнаруживались и исправлялись ошибки, в том числе несовпадение ожидаемых полей ответа с полученными данными. Теперь формат проверяется и на сервере, и перед отображением. Последняя связанная проверка включает 23 пройденных теста и совместную работу FastAPI с элементами интерфейса внутри процесса. После последних изменений настоящий сетевой запуск и внешний вид ещё нужно окончательно проверить в Ubuntu; предыдущую версию пользователь уже открывал в браузере.

В результате получился прототип, который помогает перейти от сохранённых ответов к понятному плану повторения. Его практическая ценность — в связи анализа с учебными материалами и объяснении порядка тем. Дальше можно расширять библиотеку и проверять, насколько маршруты помогают ученикам. Такой педагогический эффект пока не измерялся.

## Словарь: термины простыми словами

| Термин | Что это означает и как связано с проектом |
|---|---|
| **Датасет** | Набор примеров для анализа. Здесь — записи ответов учеников ASSISTments. |
| **CSV** | Текстовый файл с таблицей: строки и разделённые столбцы. Так получена исходная история. |
| **База данных** | Организованное хранилище, из которого можно выбирать связанные сведения. Например, ответы одного ученика и названия их навыков. |
| **SQLite** | Средство работы с локальной реляционной БД без отдельного сервера. Файл проекта — `edupath.db`. |
| **Машинное обучение** | Подбор параметров по известным примерам, чтобы делать прогнозы для других случаев. Модель изучает связь истории с правильностью ответа. |
| **Модель** | Сохранённое правило расчёта с обученными параметрами. В проекте оно превращает историю и навык в вероятность следующего ответа. |
| **Логистическая регрессия** | Модель, которая объединяет признаки и выдаёт вероятность одного из двух результатов. Здесь — правильного ответа. Слово «регрессия» не мешает использовать её для классификации. |
| **SGD** | Способ постепенно менять параметры модели по ошибкам на отдельных примерах. Полное русское название — стохастический градиентный спуск. |
| **Признаки** | То, что модель знает перед прогнозом: например, число прошлых ответов и прежняя успешность по теме. |
| **Обучающая выборка** | Данные, на которых подбираются параметры. Здесь — 223 463 ответа 3330 учеников. |
| **Тестовая выборка** | Отложенные данные для проверки готовой модели. Здесь — 59 642 ответа 833 других учеников. |
| **Целевой результат** | То, что хотим предсказать. Поле `correct`: 1 — правильный ответ, 0 — ошибочный. |
| **Accuracy** | Доля случаев, где правильно выбран класс ответа. У модели — 0,7121, примерно 71,21%. |
| **ROC-AUC** | Показатель того, насколько хорошо вероятности различают правильные и ошибочные ответы. У модели — 0,7276; это не процент верных классификаций. |
| **F1** | Совместная оценка точности положительных предположений и полноты найденных положительных случаев. Здесь положительный класс — правильный ответ. |
| **Log Loss** | Ошибка вероятностного прогноза, которая особенно штрафует уверенные промахи. У модели — 0,5653; меньше лучше. |
| **Базовый метод, baseline** | Простой способ, с которым сравнивают модель. Например, всем выдавать постоянную вероятность из обучающей истории. |
| **Утечка данных** | Использование информации, которой при настоящем прогнозе ещё нет. Например, включить текущий правильный ответ в его же признаки. |
| **API** | Согласованный способ обмена между частями программы: какие запросы можно сделать и какой ответ получить. |
| **Backend** | Серверная вычислительная часть. В проекте читает SQLite, применяет модель и строит план. |
| **Frontend** | Видимая пользователю часть: страницы, таблицы, кнопки и переходы. Она получает результаты серверной части. |
| **FastAPI** | Python-инструмент, который помогает организовать API, проверять запросы и выдавать ответы. Сам по себе он не является ML-моделью. |
| **Streamlit** | Средство создания интерактивного интерфейса средствами Python. Здесь через него выбирают ученика и изучают план. |
| **JSON** | Текстовый формат для списков и полей данных. В нём хранится модель и передаются ответы API. |
| **ID** | Идентификатор — код записи. Код навыка позволяет связать прогноз, историю и материал, даже если название совпадает с другим. |
| **Граф зависимостей** | Темы и стрелки между ними. Стрелка «площадь круга → поверхность цилиндра» указывает предварительную основу. В проекте пять таких рёбер, заданных вручную. |
| **Индивидуальная траектория** | В этой работе — последовательность повторения, выбранная по истории конкретного ученика и зависимостям тем. Это не полный многолетний учебный план. |
| **Контракт данных** | Договор о необходимых полях и их смысле. Контракт версии 2 не позволяет незаметно использовать старый неполный ответ API. |
| **Сессия** | Текущее взаимодействие пользователя с приложением. Отметки шагов живут в ней, а не в постоянной истории ответов. |
| **Интеграционная проверка** | Проверка нескольких частей вместе. Здесь проверялось, как сериализованные ответы FastAPI принимает интерфейс. |
